# 33JACK V2 — Celo Agent Payment Infrastructure (alpha)

**Development branch:** `v2/celo-agent-infrastructure`. The original Solana 33JACK app on `main` is not modified.

V2 reuses the existing 33JACK invoice intelligence, channel adapters, approval UX, and reconciliation architecture. It introduces a separate, **Celo-Mainnet-only** payment gateway that external AI agents can integrate through JSON APIs. The first phase is deliberately **non-custodial**: agents prepare requests but a payer wallet must approve and sign every transfer.

## First working slice

- `/v2` — wallet-connected Celo USDC transfer console (source `public/v2.html`)
- `GET /api/celo-v2?action=manifest` — agent discovery manifest
- `GET /api/celo-v2?action=health` — verify RPC really responds as chain 42220
- `POST /api/celo-v2?action=prepare` — construct unsigned Celo USDC ERC-20 transfer calldata with validation and configured per-payment cap
- `POST /api/celo-v2?action=verify` — independently verify matching native USDC Transfer event from a successful Celo Mainnet transaction and return a real explorer link

### Prepare: other agents call this

```bash
curl -X POST 'https://YOUR-V2-DEPLOYMENT/api/celo-v2?action=prepare' \
  -H 'Content-Type: application/json' \
  -d '{"requestId":"supplier-1001","recipient":"0x1111111111111111111111111111111111111111","amount":"0.25"}'
```

**Important:** preparation only returns calldata. It cannot send, sign or authorize a transfer on behalf of a payer. An integration must have the payer independently review and sign the exact transfer with a wallet or pre-authorized smart-account policy. There is no server-side key.

### Verify an actual transfer

```bash
curl -X POST 'https://YOUR-V2-DEPLOYMENT/api/celo-v2?action=verify' \
  -H 'Content-Type: application/json' \
  -d '{"txHash":"0x<64-hex-characters>","recipient":"0x1111111111111111111111111111111111111111","amount":"0.25"}'
```

Verification checks Celo chain ID, successful receipt, native USDC token address, recipient, integer token units and (if supplied) payer address. It does not claim that a verified transaction corresponds to a persisted invoice or a previously issued intent; those bindings require phase-two durable intent storage.

## Celo network parameters

- Chain ID: 42220 (`0xa4ec`)
- RPC: `https://forno.celo.org` (replaceable with `CELO_RPC_URL`)
- Explorer: https://celoscan.io
- Native USDC: `0xcebA9300f2b948710d2653dD7B07f33A8B32118C` (6 decimals)
- Gas token: CELO
- Source: Circle's [USDC on Celo](https://www.circle.com/multi-chain-usdc/celo)

## Server configuration

```dotenv
CELO_RPC_URL=https://forno.celo.org
CELO_MAX_USDC_PER_PAYMENT=100
```

Use a dedicated deployment and a **separate database and webhook configuration** for V2. Do not point two production instances at the same mutable state without an explicit migration plan.

## Not shipped yet — grant application blockers

- ERC-8004 registration and Self Protocol Agent ID binding
- Real authenticated external-agent identity, signed intent claims, sybil-resistance, per-agent policy and rate limits
- Durable, idempotent payment intents, invoice-to-receipt reconciliation, webhooks and audit trail
- Smart account / delegated permissions / agent-autonomous micropayments or escrow
- Production penetration tests, monitoring, abuse prevention and API credential management
- **Confirmed Celo Mainnet transactions generated by the product**; deployment and actual signed transactions are still needed
- Activation evidence: first ten real third-party agents, SDK integration examples and adoption metrics

The V2 alpha is infrastructure foundation, **not yet eligible to claim proven live mainnet usage** for the Prezenti Frontier Grant. Do not present prepared requests as completed settlement.
